Anthropic предлагает отдать Claude реактивную работу дата-инженера: упавшие пайплайны, устаревшие данные, непонятные скачки KPI. Тогда у людей остаётся время на архитектуру. Главный тезис вебинара: ума модели уже хватает, а недостаёт **интеграции** в ваши системы и **контекста** о том, как принято работать в команде. Точность определяют контекст и проверка, а не генерация кода.

::fig integration-context "Интеграция слева, контекст справа"

Интеграция — это MCP к dbt, хранилищу, оркестратору (Airflow или Dagster) и дашбордам. Доступ идёт через отдельные сервисные аккаунты с ограниченными правами. Запускать можно по расписанию, слэш-командой или через cron, все действия пишутся в журнал, а работать можно из любого интерфейса, хоть из терминала, хоть из VS Code. Контекст складывается из трёх слоёв. **Skills** — процедуры и ранбуки: утренний брифинг, PII-аудит, триаж. **Memory и CLAUDE.md** — нормы команды и выводы из прошлых инцидентов. **Semantic layer** — единые определения метрик. Писать skills и memory с нуля не нужно: черновик делает Claude, человек правит.

***

Первое демо — skill «утренний брифинг». Он проверяет свежесть пайплайнов и алерты оркестратора, сортирует по приоритету 50+ сообщений в Slack, показывает PR в ожидании ревью и сверяет дашборды через Claude in Chrome. Заодно он смотрит, чем заняты другие сессии Claude, и передаёт задачу той, у которой больше контекста. Собрали его так: рассказали свою рутину в терминал, Claude написал первую версию, потом несколько дней давали отзыв после каждого запуска. Хорошо он заработал примерно через две недели.

::fig morning-briefing "Утренний брифинг: всё важное за минуту"

Второе демо — расследование. Дашборды разошлись, потому что устарел rollup. Rollup устарел, потому что упала задача выше по цепочке. А упала она из-за ячейки «TBD» в Google Sheet, в строке 5415. Claude готовит команду, но в проде выполняет её только с разрешения человека. Потом он перезапускает задачу и пишет черновик апдейта для стейкхолдеров.

::fig incident-chain "Цепочка инцидента: от симптома к причине"

> Закрывать нужно весь класс багов, а не один случай.

Дальше реакция переходит в профилактику. Валидация появляется во всех таблицах, а владельцам чужих таблиц уходят письма. Отдельный PR делает импорт безопасным: плохая ячейка превращается в строку-предупреждение, а не роняет загрузку. В review-бот для PR добавляется новое правило. Последний приём — начинать с дизайн-дока, а не с кода. Claude получает прошлый код, вопросы из Slack и требования. Каждое решение хранится строкой: булевы колонки-факторы плюс человекочитаемая причина («засчитано, потому что A, B, C»). Переопределения вносятся через seed-CSV без кода и замораживаются по lock date. Док служит контрактом с Claude, а пограничные случаи описывают словами, и Claude превращает их в тесты.

***

В ответах на вопросы прозвучали практичные нормы. CLAUDE.md держат в пределах 200–250 строк, чистят при каждом релизе модели и делят на файлы по темам. Доверие наращивают постепенно, с детерминированными тестами и evals там, где это возможно: сначала одно место, потом масштаб. Skills — общие процедуры команды, memory — знания и личные предпочтения, и всё это живёт в репозитории рядом с semantic layer. Для разбора сбоев одних логов мало, Claude нужен ещё доступ к коду.

Для личного бота, который строит планы Б, отсюда получается готовый рецепт. Утренний брифинг рисков показывает, какие планы под угрозой, и улучшается по отзыву после каждого запуска. В журнал сбоев пишется «план А сорвался из-за X, сработал план Б Y», чтобы бот замечал повторяющиеся паттерны. Каждое решение хранится строкой с условиями и причиной. Необратимые действия выполняются только после «ок»: бот готовит действие и черновик, а подтверждает человек. После сбоя закрывается весь класс проблем и дополняется чеклист. CLAUDE.md остаётся коротким и разбитым по темам.
